# Create an MR

This document outlines the workflow and guidelines for creating a GitLab merge request.

## Workflow

1. Ask the user which branch to target. Assume the current branch is the source branch.
2. Determine the GitLab issue(s) related to this MR.
   - First, try to infer from the source branch name.
   - Second, try to infer from `git log --oneline`.
   - If you're still unsure, ask the user for issue IDs.
2. Create the MR with autogenerated description:

    ```bash
    glab mr create --draft --fill \
        -t <issue-title> \
        --target-branch <target> \
        -a <me> \
        -i <issue> \
    ```

3. Add the Markdown-formatted MR description using an MR template if one can be found:
    1. Look for MR templates in `.gitlab/merge_request_templates`.
    2. If none are found, run:

        ```bash
        glab api projects/:fullpath/templates/merge_requests
        glab api projects/:fullpath/templates/merge_requests/<template-key>
        ```
    
    3. Create a temporary file with the MR description.
        - If you have a template, follow it **very** carefully.
        - If no template was found, use [this default](../templates/default-mr-description.template.md).
    4. Add your description to the MR:

        ```bash
        glab mr update <mr-id> -y --description "$(cat <path-to-desc-file>)"
        ```

4. *If* related issues were found, add their labels and milestone to the MR metadata.
    - View issue labels and milestone: `glab issue view <id> --output=json --jq '{ labels: .labels, milestone: .milestone }'`
5. Verify the MR creation was successful: `glab mr view <id>`

## Guidelines

- **Always** assign me to the MR. This is important for project management.
- **Never** mark the MR as ready on your own. That will be done by me.
- **Always** use conventional commit format for MR titles.

### Writing descriptions

- **Always** follow the template very closely.
- **Always** use a temporary file when writing the description. This avoids any weird shell escaping issues with code blocks and ensures all Markdown is formatted correctly.
- **Always** use relative filepaths if you need to reference specific files in the repo. **Never** use absolute filepaths from my workspace

When writing testing/review steps:

- **Always** use checklists unless the template explicitly says otherwise.
- If applicable, provide commands to run for testing (in backticks).
